# htgame：保留 Web 优势的完成度提升方案（Roadmap SOP）

日期：2026-10-22。本文件取代旧版 02 的全量路线，作为当前推荐实施方案（Roadmap SOP）。01 保留为当时的审计快照；03 的所有权与小批合并原则继续适用，但任务范围以本文为准。

## 1. 产品目标：小而完整、可长期保存的 Web 沙盒

定位为：**参考 Minecraft Java 1.20.x 的核心规则，保留快速进入、自由建设和持续探索的轻量浏览器沙盒。** 不宣称完整兼容某个原版版本。

完成度按玩家能否走通玩法衡量，而不是按原版条目覆盖率：

- **建设**：取得材料、设计建筑、使用常见形状与装饰、保存后继续建设。
- **经营**：种植养殖、制造装备、附魔修理、交易，再逐步自动化一部分劳动。
- **冒险**：发现结构、面对明确风险、获得有用奖励，最终完成一个可选择的终局目标。

短会话也能获得进展，长会话仍有自由建设的空间；不为了“快节奏”强行缩短全部生存过程。用户已体验确认的现有基础功能继续保留，不再把重复验证启动/进出游戏当作本轮任务。

旧设计的问题主要是把“全面复刻所需的架构与内容”放进了默认路线，超出当前产品目标。接口、存档版本、模块边界仍有价值，但无需一次性建设可扩展到所有版本的通用引擎。

## 2. 对轻量化判断的修正

| 判断 | 本方案的处理 |
|---|---|
| 保持纯 JS、静态分发、预烘焙资产 | 采纳。日常修改无需装 Node 或执行打包，玩家无需安装运行环境 |
| 固定 `Y=0..255` | 采纳。保留当前 16 个区段和索引，新增维度也先沿用同一高度范围 |
| `Uint16` 足以支撑计划内容 | 采纳。暂不使用全量 `Uint32` 或区段 Palette；保留 `meta`/`light` 的 `Uint8` |
| 一个 CPU Worker 作为起点 | 采纳，但它只减少主线程计算阻塞，不保证消除所有卡顿 |
| TS 或文件变多就必然把首包变成 40–80MB | 不成立。源码组织、工具链与玩家下载资源是不同问题；本项目因维护成本选择继续 JS，而不是因为 TS 必然产生大首包 |
| 全包导入、运行时通用模型兼容 | 不采用。只预烘焙实际选用资源，既不装载全部 PNG，也不接入全部 OGG |
| 任意分包都损害 Web 体验 | 不成立。按需资源与缓存本来可以减少首包；当前体量可先用一个资产包，只有预算需要时再增加少量固定资源组 |
| `384高度 × Uint32` 使整个区块变为 6 倍 | 仅对 `block` 数组成立；若 `meta`/`light` 仍 `Uint8`，三个主要数组合计为 `3.00×`。稀疏存储则另算 |
| 70% 工作量只贡献 5% 乐趣 | 没有项目数据支撑，不作为量化依据。考古、嗅探兽等在当前目标下延期，但不否认它们对特定玩家的价值 |
| 单个文件 / 1.8 万行是硬边界 | 改为维护预警。不能为满足行数而压缩可读性、删掉检查或制造大文件 |

> 注：“铜灯”属于 1.21 内容，不纳入当前 1.20.x 参考范围。

### 当前体积与内存的准确口径

按文件长度读取：当前 `game` 目录排除页面未加载的 `assets.vanilla.js` 后，页面静态文件总计约 `0.92 MB`（十进制，已剔除 `game.js` 内重复的 `Redstone` 副本）。这不是浏览器解码后内存、GPU 占用或压缩传输量，也不能据此直接等同于固定 0.5 秒进入世界。

每个 `16×16×256` 区块有 `65,536` 格，只计 `block` / `meta` / `light` 三个基础数组：

| 布局 | block | meta+light | 合计 | 相对当前 |
|---|---:|---:|---:|---:|
| 当前：256 高、block `Uint8` | 64 KiB | 128 KiB | 192 KiB | 1.00× |
| **推荐：256 高、block `Uint16`** | **128 KiB** | **128 KiB** | **256 KiB** | **1.33×** |
| 假设：384 高、block `Uint32` | 384 KiB | 192 KiB | 576 KiB | 3.00× |

推荐方案仅增加 `64 KiB/区块`，400 个区块增加 `25 MiB`。以上不含网格、颜色、对象、存档缓存、Worker 快照和 GPU 资源；真正的大头必须分别统计，不能只优化数组类型。

## 3. 明确保留、删除和按需实施的设计

| 保留且值得做 | 暂不做 | 有证据再做 |
|---|---|---|
| 物品原子操作、保存成功后清 dirty、未加载实体保留 | 全面 TS 化、目录大迁移、通用 ECS / 依赖注入 / 插件框架 | 大规模 Palette 压缩 |
| `Uint16`、高 ID 安全、稳定 ID 清单、紧凑图标索引 `iconIdx` | `-64..319` 高度重构、原版同种子逐格一致 | 第二个 Worker 或模拟线程 |
| 单 Worker 与主线程任务预算（生成与跨块光照分离） | 通用资源包/数据包解析器、CTM/CEM 全兼容 | 复杂透明排序、更多网格优化 |
| 明确的保存版本、旧档迁移与 `modifiedChunkKeys` 索引 | 完整 Java 红石边缘行为、机器/复制器全兼容 | 两三个固定资源分组 |
| 一份资源构建入口与引用白名单 | 所有木族/染色/生物/结构逐项追平 | 少量选定 JSON 模型的离线转换 |
| 少量局部模块与文档化接口 | 全部 1.20.5/1.21 更新、多人/原版服务器协议 | 离线缓存/PWA 分发便利性 |

不需要全量 registry 框架。保留现有 `BLOCKS`、`ITEMS`、`BID` 和 `defBlock` 即可，把容量、稳定编号、紧凑图标槽位和存档映射处理正确。不要为了轻量化放弃数据一致性。

## 4. 最小技术演进与代码级防护规则

### 4.1 发布方式：同一套游戏代码，两种进入方式

- **主分发**：静态网页链接，无账号、无安装。服务器只提供静态文件，不需要游戏后端。
- **便携分发**：下载文件夹后双击 `index.html`；保留当前经典 `<script>` 加载。必要时由一个 Python 发布脚本生成自包含 HTML 和 Worker 源码，脚本由开发者运行，玩家不用构建。
- 平时修改 JS 直接刷新；只有变更素材或生成便携发布物时才运行预烘焙脚本。保持已有 Python 资源工具即可，不新增完整前端工具链作为前置条件。
- 无需把“一个文件”作为产品要求。几个静态 JS 文件同样可以免安装、离线使用，且更容易修改。

`file://` 的来源策略因浏览器而异，不能保证外部 Worker、模块加载和存储在每个浏览器行为一致。发布版可尝试自包含 Blob Worker；构造失败、初始化报错或没有 ready 回执时，自动切换到同一计算函数的主线程分步队列，必要时减小视距。不能要求用户关闭浏览器安全策略。静态 HTTP/HTTPS 路径作为完整性能路径。依据：[MDN 文件来源说明](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy)。

便携模式是同一机制的性能降级，不另维护一套玩法。浏览器存储不可用时明确告知并提供导出，不能安静地把临时内存当作永久保存。

### 4.2 `Uint16` 升级：改得少，但必须改完整（含 `iconAtlas` 解耦）

至少检查并同步修改以下 8 个位置：

1. `world.js:19` 的 `Chunk.blocks` 改 `Uint16Array`。
2. `mesher.js:48` 的邻域 `ids` 缓冲改 `Uint16Array`，否则渲染时仍会按 8 位截断高 ID。
3. `world.js:5–7` 的按 block 索引属性表（`SOLIDCUBE`、`OPAQUE`、`OPACITY`、`LIGHT_EMIT`、`IS_FLUID`、`REPLACEABLE`）扩大容量和遍历范围；表中 `0–15`/布尔值仍用 `Uint8Array`。
4. `blocks.js:11` 的表容量与边界检查；不要把字体、噪声、颜色等所有 `256` 常量一刀切替换。
5. `util.js:197–200` 的 `rleDecode` 不再固定返回 `Uint8Array`；由调用方指定目标类型或直接解码写入既有数组。
6. `save.js` 的格式标记与旧档读取。现有 RLE 记录本来就用 `Uint16` 存储“值、长度”对，不能仅通过其数组类型判断旧/新世界格式，需显式记录 `schemaVersion` / `blockBits`。
7. `blocks.js` 的独立物品原本从 `256` 开始，而方块物品也占用 `ITEMS[id]`；若方块突破 `255` 直接延伸到 `256+`，会与既有独立物品 ID 发生冲突。
8. **[防护规则 #1] `render.js:786` 与 `ui.js:136` 的图标图集（`iconAtlas`）紧凑索引解耦**：
   - 现状 `buildIcons()` 直接按 `Math.max(...ids)` 分配 2D Canvas 行数，若新编号跳至 `1024+` 会导致图集画布高度膨胀 3 倍且中间充满空白。
   - 改造要求：在注册物品/方块时分配紧凑递增的图标序号 `it.iconIdx = 0..N-1`，`buildIcons()` 与 `UI.prototype.drawItem()` 一律按 `it.iconIdx` 计算图集行列坐标，彻底解耦“稀疏持久化 ID”与“GPU/Canvas 图标图集尺寸”。

**最小 ID 分配方案**：冻结所有既有 block/item 编号（`0..380` 区间），新增方块与新增物品从明确未占用的稳定区间（如方块从 `512` 起、新增独立物品从 `1024` 起，或统一在 `ids.js` 清单中显式指定固定数值）分配；以后只追加、不重排、不复用退役编号，并在启动时校验 ID 唯一性。

`meta` 仍保持 `Uint8Array`，通过少量 `getFacing`/`getPower` 等辅助函数明确各 block 的位含义；少数复杂数据放 `blockEntity`，不提前制造所有方块的通用状态组合。

### 4.3 一个 Worker，一条受控任务队列（含跨区块光照边界规则）

```text
主线程：输入 / 20TPS玩法 / 权威世界 / 跨块光照(initLight) / 保存 / WebGL上传与绘制
        ↓ 小任务与不可变快照                   ↑ 可转移结果(Transferable)
CPU Worker：纯单区块地形生成(generate) / 18³邻域section网格构建(Mesher.build)
```

- **单飞与主线程优先级队列**：初始同时只运行 1 个在途 Worker 任务，待办队列保留在主线程，按“玩家刚编辑的邻近 section 网格 → 近处缺失区块生成 → 远处预加载”排序并按坐标去重，不提前向 Worker 塞入数百个无法撤回的旧任务。
- **网格任务（优先迁移）**：按 section 计算，输入使用现有 `18³` 邻域形状（`ids`、`metas`、`lights` 及草/叶色表），并附 `worldSessionId`、`dimension`、坐标、`revision`。返回结果过期或切世界后直接丢弃。
- **[防护规则 #2] 生成任务与跨区块光照（`initLight`）职责切分**：
  - `World.prototype.initLight(ch)` 需要读写相邻区块（`cx±1, cz±1`）的光照边界，不能在只有单区块上下文的 Worker 内直接完成。
  - 因此 Worker 的 `generate(cx, cz)` **仅执行纯单区块计算**（产出 `blocks`、`metas`、`biome`、`grass`、`foliage` 及结构蓝图标记 `village`），通过 Transferable `ArrayBuffer` 交回主线程挂载进 `w.chunks` 后，由主线程按帧预算执行 `initLight(ch)` 与首次生物生成。
- **所有权安全**：只转移新生成的数据、专用快照拷贝或网格结果，严禁把主线程活跃世界的 `ch.blocks` / `ch.lights` 原数组直接放入 Transferable 列表导致主线程 ArrayBuffer 被 detach。依据：[MDN Worker](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers)、[可转移对象](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Transferable_objects)。

### 4.4 存档可靠，但保持简单（含 `modifiedChunkKeys` 防覆盖保护）

第一版只需要 `schemaVersion`、`registryVersion`、`generatorVersion`、`blockBits`、当前维度与必要状态，不引入大型日志服务或通用持久化框架。

- **当前代码基线状态**：M0 阶段的 4 项 P0 修复（Shift 批量合成 `canFit` 原子校验、拖拽/双击 `sameStackMeta` 保护、`saveWorld` 提交成功后清 dirty、未加载 `pendingMobs` 与 `enchantSeed`/`spawnedChunks` 持久化，以及删除 `game.js` 重复红石代码）**均已合入当前主分支并验证通过**。
- **[防护规则 #3] 淘汰 `savedChunks` 冷数据时必须保留 `modifiedChunkKeys` 内存集合**：
  - 现状 `loadChunk(cx, cz)` 为同步判断：若 `w.savedChunks.get(ck)` 为空，会立即调用 `w.generate(cx, cz)` 重新生成初始地形。
  - 当引入 LRU 淘汰 `w.savedChunks` 中的冷区块数据时，内存中必须常驻一个极小的 **`modifiedChunkKeys = new Set()`**（即使记录 10,000 个修改过的区块 key 也仅占约 80 KB）。
  - 只要 `modifiedChunkKeys.has(ck)` 为真且内存 `savedChunks` 未命中，`loadChunk` 必须走异步 IndexedDB 单块读取并等待返回，**严禁回退调用 `w.generate(cx, cz)` 覆盖玩家建筑**。
- **区块卸载与冻结**：保存尚未加载的持久实体、附魔 seed 和计划事件；区块卸载后冻结其模拟，重新加载才继续。跨维度农场不在后台运行。
- **导出/导入备份**：提供世界 JSON/二进制文件导出与导入及版本升级前自动备份，不将浏览器 `beforeunload` 事件作为唯一保存保障。

### 4.5 只做必要的局部拆分

继续沿用现有 `game/js` 目录和经典脚本加载。按阶段逐步抽出：
- `world-worker.js`（Worker 入口与主线程队列适配）
- `trading.js`（W1 村民职业、交易表与补货）
- `automation.js` 或扩充 `redstone.js`（W1/W2 漏斗、比较器、活塞、侦测器）
- `dimensions.js`（W3 下界、要塞与末地龙战）

不预建几十个空目录。每次仅当一个职责已经独立、重复出现或妨碍并行时抽取模块。所有物品修改必须走共同事务、所有世界修改必须走共同更新入口。

## 5. 资源策略：用好现有包，增加表现收益

- `assets.js` 继续作为主要预烘焙资产。构建器 `tools/build_from_pack.py` 只读取白名单中的贴图，而非打包 ZIP 全部 6,924 个文件；已彻底废弃冗余的旧脚本入口。
- 普通方块复用现有 `SH_CUBE` / `SH_BOXES` / `SH_MODEL` / `SH_CROSS`。特定复杂模型只做选定模板或离线转换，不开发通用 Minecraft 资源包运行时。
- 水、岩浆、火的动画时间线离线烘焙，运行时只读紧凑帧表；不在浏览器解析全量 `.mcmeta`。
- WebAudio 保留。先挑 8–12 类辨识度高的声音事件按需补充；不以 355 个 OGG 全部接入为目标。
- 仍检查 GPU 3D/Array 纹理层数上限（`gl.MAX_ARRAY_TEXTURE_LAYERS`，WebGL2 保底 256，主流桌面 GPU 为 2048，当前为 457 层）。新增方块贴图时优先复用现有面材质并监控总层数。

### 关键玩法的工程约束（防止复杂度爆炸）

- **[防护规则 #4] W2 活塞（Piston）不可推动黑名单**：
  - 沿用原版铁律：**所有带 `blockEntity` 的方块（箱子、熔炉、漏斗、刷怪笼）、附魔台、铁砧、黑曜石、基岩、门、床、已伸出的活塞均不可推动**，从而保证 `blockEntities` 的 `"${x},${y},${z}"` 坐标键永远不会因活塞推动而失步。
  - 单次推动方块数量上限固定为 `12` 格；路径上的脆弱方块（火把、红石线、中继器、拉杆、按钮、农作物、蜘蛛网）被推动时直接触发 `breakBlock` 掉落成物品。
- **[防护规则 #5] W3 多维度（下界/末地）轻量单活切换架构**：
  - 既然跨维度农场不在后台运行，内存中的 `World` 与 `Renderer` **保持单维度数据结构不变**，无需在所有 `getBlock(x, y, z)` 和 `ckey(cx, cz)` 调用上增加 `dimension` 参数。
  - 玩家穿过下界传送门或末地传送门时：先将当前活动维度的脏区块与实体快照写入 IndexedDB（存档表按 `${dim}:${ckey}` 区分维度），随后清空内存中的 `world.chunks` / `renderer.sections` / `entities`，切换 `world.dimension = 'overworld' | 'nether' | 'end'`，再从目标维度的存档与生成器流式加载。

### 推荐发布顺序

## 7. 用四类预算决定何时停止扩张

### 边界一：分发与进入
- 默认发布目录上限 `7 MiB` 未压缩（不计源 ZIP、工具、备份与未引用 fallback）。
- 核心首次传输目标 `≤ 3 MiB`，缓存命中/本地启动以首次可操作 `≤ 1 秒` 为争取目标。

### 边界二：帧耗时与有界内存
- 默认视距 `6–8`、活动模拟半径约 `4` 区块。
- 稳定场景目标：中位帧耗时 `≤ 16.7ms`、P95 `≤ 33.3ms`；加载区块 `≤ 320`，世界 CPU 数组与任务快照 `≤ 96 MiB`，估算 GPU 网格缓冲 `≤ 128 MiB`。
- 正常往返探索后内存应趋于平台；若 `savedChunks` 或 Worker 队列持续无界增长，立即冻结功能开发先修生命周期。

### 边界三：范围与维护
- 以 `250–300` 种非空气方块、`4–6` 种代表性结构、少量高辨识度生物为目标范围。
- `Y = 0..255` 为本版明确硬边界；源码 `15,000–18,000` 非生成行作为复审信号。

### 边界四：正确性与新增价值
- 出现已知物品增殖、存档丢失、实体消失或无法恢复世界的问题时，冻结功能扩张，优先修复。
- W3 的建设、经营、冒险三条链全部连通后，转入稳定维护。
